# 阶段 A 实施计划:能力契约和适配层

依据 `docs/agent-workflow-orchestration-implementation.md` §12 阶段 A,新增统一能力契约、registry 和适配层,注册 7 个 capability,并将 `ai_service.py` 视觉分支改走 `execute_capability`,满足验收标准「同一 capability 可以被主服务和 Runtime 以统一方式调用」。本轮不新增数据库表(WorkflowRun 持久化属于阶段 B)。

## 1. 新增 `backend/app/services/ai_capability_contracts.py`(契约层)

常量与模型,遵循现有 `ai_agent_contracts.py` 的 Pydantic v2 惯例(snake_case、`schema_version` Literal 字段、`extra="forbid"`):

- `CAPABILITY_SCHEMA_VERSION = "agent_capability_v1"`、`CAPABILITY_RESULT_SCHEMA_VERSION = "capability_result_v1"`
- `CapabilityStatus` Literal:`success | empty | waiting_async | waiting_user | failed`
- 输入模型:
  - `VisionSkillInput`:`conversation_id`、`content`、`attachments`(list of `{type, url, mime_type}`,复用现有附件结构)——三个视觉 skill 共用
  - 检索能力复用 `ai_agent_decision_contracts.py` 现有的 `SearchPhotographersInput` / `SearchPortfolioItemsInput` / `SearchPackagesInput` 作为 `input_model`
  - `CreateInspirationDraftInput`:`reference_text`、`images`
- 输出数据模型(通过 output schema 校验的 data 才能进 workflow context):
  - `ImageAnalysisData`:对齐 `normalize_vision_analysis` 的 `vision_analysis_v1` 输出(`summary/style/scene/mood/makeup/lighting/color/composition/search_terms/attachments/provider`),外加派生字段 `search_query`(由 `build_vision_search_text` 生成,供阶段 D 的 `$context.image_analysis.search_query` 模板使用)
  - `SkillReplyData`:`schema_version`(work_appreciation_v1 / style_analysis_v1)、`reply`(自由文本)
  - `SearchData`:对齐 `agent_search_tool_v1`(`resource_type/count/resource_ids/items/criteria/diagnostics`)
  - `InspirationDraftData`:对齐 `create_inspiration_draft` 的 result
- `CapabilityError`:`code`、`message`、`retryable`
- `CapabilityProvenance`:`capability`、`attempt`、`duration_ms`、`tool_name`、`provider` 元信息
- `CapabilityResult` 信封:`schema_version`、`capability`、`status`、`data: dict | None`、`artifacts: list`、`warnings: list[str]`、`error`、`provenance`

- 模块命名空间导入 `from backend.app.services.ai_provider import get_ai_provider`(测试可 monkeypatch 本模块);`_build_provider_messages`、`_image_url_for_provider` 从 `ai_service` **函数内惰性导入**,避免 ai_service → registry → adapters → ai_service 的循环导入

  - `vision.appreciate_image` / `vision.analyze_style`:取 content 自由文本

## 3. 新增 `backend/app/services/ai_capability_registry.py`(registry 与执行入口)

- `CapabilitySpec` frozen dataclass(对齐现有 `ToolSpec` 风格):`name`、`kind: "skill"|"tool"`、`input_model`、`output_model`、`execution_mode: "sync"|"async"`、`retryable`、`timeout_seconds`、`requires_confirmation`、`allowed_roles`、`idempotent`、`description`、`adapter`
- `CAPABILITY_REGISTRY` 注册 7 个能力:三个 vision skill + 三个检索 + `inspiration.create_draft`
- `execute_capability(db, *, name, input, user=None, conversation_id=None, message_id=None, attempt=1, idempotency_key=None, vision_analysis=None, request_content=None) -> CapabilityResult`:
  1. 未注册能力 → failed 信封(`unknown_capability`)
  2. 用 `spec.input_model` 校验并归一化输入,未知字段拒绝(`invalid_input`)
  3. 计时调用 adapter;异常捕获 → failed 信封(`capability_error`,含 retryable)
  4. 用 `spec.output_model` 校验输出(`invalid_output`)
  5. 组装 `capability_result_v1` 信封 + provenance
- 辅助:`get_capability_spec()`、`list_capabilities()`(供未来 planner/阶段 C runtime 使用)
- 超时与重试本轮只在 spec 中声明策略,**不做运行时强制**(文档把 enforcement 归在阶段 C)

## 4. `ai_service.py` 视觉分支改造(行为保持等价)

- L3918-3948:三个视觉 skill 的内联 provider 调用改为 `execute_capability(...)`,按分支取:
  - 赏析/风格:`data.reply` → `appreciation_reply` / `style_analysis_reply`,provider 元信息从 `provenance`/`data` 还原以维持现有 metadata 结构
  - 分析:`data`(含 provider)→ `vision_analysis` + `vision_provider_result` 等价物,后续 `_apply_vision_slots`、`build_vision_search_text`、`_vision_metadata` 逻辑不动
- 顶部导入 `execute_capability`;检索三分支、复合工作流分支一律不动
